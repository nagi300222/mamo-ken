# 最終報告：マモ拳 3Dキャラ3体のモデル・リグ・モーション実験

ブランチ `exp/mamoken-fable-3d`（main は未変更、成果物は `exp/fable-3d/` 以下のみ）。

## 結論

- **「動かす仕組み」は使える水準になった。** 3体とも、必須ボーン・スキニング・全10クリップ入りの GLB が Three.js で再生でき、データ検証は全項目合格。
  モーションはポーズを数値で書くだけで追加でき、1体3秒で GLB まで再生成できる。
- **「見た目」は元絵に届いていない。** 体型・配色・装飾で誰かは分かるが、顔の造形と毛並みの彫りは元絵より明らかに粗い。
  特に godan は怒り顔が出ておらず、3体の中で一番似ていない。
- 「3Dモデルの完成」と「リグの完成」を分けて評価すると、**リグとモーション基盤は合格、造形は試作止まり**。
- 採用を決める材料としては、「モーション制作の負担は確かに減る。ただしこの手続き的な造形のままでは見た目で不採用になりうる」が率直な評価。

見た目の採否はナギの判断なので、判断に使う画像と動画は末尾に一覧にした。

未達・条件つきの項目:

- 「正しい拳の形状」は部分的。横拳で親指が下半分に来る配置にはしたが、指の節の彫りは浅く、元絵のような握りの立体感は無い。

- 口は開かない。`jaw` ボーンはあごを少し下げるだけで、口の中は作っていない。

## 元絵再現度

`chars/{id}/renders/compare.jpg` に元絵と並べてある。

### moguzo（3体の中では一番近い）

似ている点: 洋梨形の体、黄土色と腹のクリーム色の塗り分け、赤いハチマキと右側頭部の結び目・垂れ、焦げ茶の拳、灰色の足と黒い爪、丸い黒目。

似ていない点:

- 元絵より背が低くずんぐりして見える。構えで膝を曲げると太ももが左右に張り出し、下半身が「ズボンをはいた」ような輪郭になる。元絵は腰から足までなめらかな洋梨形。
- マズルの立体が弱い。元絵は鼻先が前へ出て、頬のクリーム色がはっきり分かれるが、3Dは顔が平たく、口の「への字」が強すぎて少し不機嫌に見える。
- 毛並みは彫りではなくテクスチャの模様が主体で、元絵の「重なった毛束の彫刻」感は無い。腹の模様はうろこ状に見える。
- 拳は指の節の彫りが浅い。ハチマキの垂れは細い板で、布の厚みや結び目のしわは無い。
- 目に元絵の茶色い縁取りと白いハイライトの質感が無い（黒い球＋白い点）。

### pisuke

似ている点: 細身で縦長のシルエット、明るい砂色、青いリストバンド、明るい色の拳と足、後ろへ出る尻尾。

似ていない点:

- 頭が丸く、1回修正して耳を小さく鼻先を長くしたが、まだ元絵ほど鼻先が出ていない。頭頂の平たさも足りない。
- 元絵の特徴である「指の間の黒い爪」が正面から見えない（爪は指先の下側にあり、握ると隠れる）。
- ヒゲが無いので、顔の軽さ・すばしこさが出ていない。
- 毛が元絵よりのっぺりしている。構えの足の前後の開きも元絵より小さい。

### godan（一番似ていない）

似ている点: 幅広で重い体、濃い茶色と胸の明るい茶、黒帯と結び目・垂れ2本、黒いリストバンド、大きな拳、低く開いた構え。

似ていない点:

- **怒り眉が出ていない。** 眉の盛り上がりと濃い線を入れ、`brow_angry` を常時0.65かけているが、遠目には明るい斑点にしか見えず、表情は「むっとしたクマ」止まり。元絵の鋭い目つきは再現できていない。
- 顔全体がテディベア寄り。マズルの四角さと、目の上の骨ばった張り出しが足りない。
- 元絵で印象的な、肩から首を覆う逆立った毛と、深く彫られた毛束が無い。体表がなめらかすぎる。
- 帯は体に沿っているが、元絵のような帯の上下での肉の段差（締まり）は弱い。

### 3体の作り分け

同じ生成コードに体型パラメータを与えているが、単純な拡大縮小ではない。頭・胴・腕・脚の比率、肩幅、頭頂の平たさ、足の開き、マズルの形を個別に持つ。
`chars/{id}/renders/turnaround.jpg` を並べると、moguzo＝洋梨、pisuke＝細い円柱、godan＝逆台形に近い肩、と輪郭が違う。
一方で、耳・目・鼻・拳の作りは共通なので「同じ顔の系統」に見える。これが3体とも「クマっぽい」と感じる原因でもある。

## 関節の問題

`validation/deform/{id}_A_limbs.jpg`（腕・脚・拳の回転）、`_B_crouch_jump.jpg`、`_C_attack_return.jpg`、`_D_secondary.jpg` で確認した。

| 部位 | 状態 |
|---|---|
| 肩 | 腕を前へ突き出す・頭上へ上げるで、つぶれや穴は出ない。`shoulder_fix`（半分回転）と自動の鎖骨の持ち上げが効いている。godan は肩が大きいので、腕を真上に上げると肩が頭にかなり近づく |
| 脇 | 構えと腕上げの画像では穴や裏返りは見えない。腕を体に密着させる姿勢は試していない |
| 肘 | 構えやガードの深い曲げで細くならない。前腕が太いので、ガードのように強く曲げると上腕と前腕が重なって一体に見える |
| 前腕のひねり | 拳を0°→270°回しても前腕が細くならない（`forearm_twist` が半分受ける）。ただし確認は全身の画像でしており、手首まわりの拡大確認はしていない。リストバンドは前腕と手首の中間で回る |
| 股関節 | **一番弱い。** 脚が短く太ももが胴の毛に埋もれているため、脚を高く上げると太ももの毛が引き伸ばされ、脚が円すい形の「ひれ」のように見える。`thigh_fix` を入れて板状にはならなくなったが、pisuke のキックでも分かる |
| 膝 | 深い屈伸で太ももが左右に張り出す（正面から見て幅が広がる）。破綻ではないが元絵の輪郭から離れる |
| 尻尾の付け根 | なめらかにつながる。揺れても付け根が折れない |
| 足 | 足裏は床に固定できる（しゃがみ保持中のずれ0、歩きの接地中は一定速で後ろへ流れる）。つま先は接地のまま、かかとを上げられる |
| 装飾 | ハチマキ本体は頭に固定、垂れは2ボーンで揺れる。帯は胴に沿い、垂れは2ボーン。**垂れ布と体の貫通チェックは自動化していない。** godan が深く前傾したときの帯の垂れ、moguzo の被弾時のハチマキの垂れは、フレームによって体に触れている可能性がある |

しゃがみからジャンプへのクロスフェード、パンチ後の待機への復帰は、姿勢の飛びなくつながる（`_B_`、`_C_` のシート）。

## GLB互換性

- Three.js r180 の GLTFLoader でエラーなく読み込み、AnimationMixer で10クリップすべて再生できた（ヘッドレスChromium、ソフトウェアWebGL）。
- 拡張は使っていない（Draco・meshopt・KTX2 なし）。標準の PBR マテリアル＋ベースカラーテクスチャ1枚。モーフはスパースアクセサ。
- **Three.js は読み込み時にボーン名の `.` を取り除く**（`upper_arm.L` → `upper_armL`）。対応表は `docs/rig_spec.md`。
- スマホ負荷の見込み（**実機では未計測**）: 1体あたり約2.5〜2.9万三角形、36〜40ボーン、描画2回、テクスチャ1024²が1枚。
  2体同時で約5.5万三角形・描画4回なので、数年内の一般的なスマホなら問題ない範囲と見込むが、推測であり確認が要る。
  トゥーン表示の輪郭線は描画回数が倍になる。
- 軽くする余地: `characters.py` の `tris` で三角形数を下げられる。テクスチャは512²でも成立しそう。
  メッシュは無圧縮なので、Draco か meshopt をかければ GLB は半分以下になる見込み（今回は使えなかった。下記）。

## モーションの追加しやすさ

実際にやってみた結果として、ここが一番の成果。

- 1モーションは `motions.py` に「構えからの差分で書いたキーポーズ3〜5個」を並べる関数1つ。詳細は `docs/motion_authoring.md`。
- 単位が体格に依存しない（脚の長さ・腕の長さ基準）ので、同じ記述が3体にそのまま通る。
  今回の10種のうち、キャラごとに中身を書き分けたのは `stand_heavy` だけで、残り9種は共通の記述＋構えの個性（`STYLE` の数値）で済んだ。
- 肘・膝のIK、肩の持ち上げ、尻尾と垂れ布の揺れ、ループの継ぎ目、終端の収束は自動。
- 反復が速い: モーションだけ直すなら1体3秒でGLB、撮影10秒。
- 所要の目安: 単発モーション1本で、1キャラ目30〜60分、他キャラへの展開は1キャラ10〜20分。歩きなど接地の多い動きは1〜2時間。
- 弱点:
  - ポーズを数値で書くので、見栄えのする中割りやひねりは試行回数が要る。今回のモーションは「正しく動く」水準で、格闘ゲームとして気持ちいい緩急までは詰めていない。
  - 歩きは短い脚なりの小さなすり足で、地味。ジャンプの脚の折り畳みも控えめ。
  - 体へのめり込みは自動では防がない。目で見て直す。
  - .blend には IK 制御が残っているが、キーは毎フレーム打ってある。Blender 上で手付けで直す用途には向かず、直すならスクリプト側。

2Dとの比較は、2D側の1モーションあたりの実コストを私が知らないので数字では言えない。
言えるのは、「1モーション追加＝関数1つ、全キャラへほぼ自動で展開」という性質は2Dの描き起こしには無い、という点。

## 残り6キャラへの展開可能性

**前提: 残り6キャラ（hakuma, chirka, takimaru, yomikage, bullet, dark_moguzo）の絵は今回開いていない**（参照許可が3体ぶんだったため）。以下は仕組みからの見積もり。

- マーモット体型のキャラなら、`characters.py` に体型パラメータ約40個と配色を足すだけで、メッシュ・ウェイト・テクスチャ・リグ・10モーションが出る。
  今回、pisuke と godan の初版はパラメータ追加だけで出て、そのあと顔の調整に2〜3往復かかった。1キャラ半日〜1日が目安。
- dark_moguzo が moguzo の色違いに近いなら、最も安い（配色と表情の差分）。
- 新しい装飾は生成コードが要る。帯・ハチマキ・リストバンドは「体表に沿う輪」と「垂れ布」の2部品で作ったので、
  首巻き・腕輪・腰布の類は流用できる。帽子・マント・武器・長い髪のようなものは新規で、1種類あたり数時間〜1日。
- モーションは共通記述がそのまま使える。武器持ちや体型が大きく違うキャラは、構えと攻撃を書き分ける必要がある。
- 一番のリスクは造形の天井。手続き的な形の足し合わせでは、顔の個性を元絵の水準まで出せない。9体並べたときに「同じ顔の色違い」に見える恐れがある。

見た目が不採用になった場合の現実的な案（**未検証**）: リグ・モーション・検証の仕組みは残し、メッシュだけを手作業のスカルプトや別の方法で作ったものに差し替える。
ウェイトは頂点の位置から計算しているので、体格が近いメッシュなら同じ計算を当てられる可能性がある。

## 使えなかったツールと代替手段

| 使えなかったもの | 代替 |
|---|---|
| `blender` コマンド（未インストール） | `pip install bpy`（5.3.0）を Python モジュールとして使用 |
| EEVEE / Workbench レンダラ（`libEGL` が無くヘッドレスで初期化できない） | 造形の初期確認は Cycles（CPU）。納品用の画像・動画はすべて Three.js プレビューをヘッドレスChromiumで撮影（実際のGLBの見え方になる） |
| glTF の Draco / meshopt 圧縮（bpy の pip 版にライブラリが入っていない） | 無圧縮で書き出し。サイズは1.7MB前後 |
| Blender のテクスチャベイク | 使わず、numpy で位置ベースの焼き込みを自作（UV展開は xatlas） |
| 手作業のスカルプト・ウェイト塗り | 使わず、SDF（距離関数）の合成とマーチングキューブで造形、ウェイトも形状から計算 |

方式の切り替え: 当初は Blender 内で形を組む想定だったが、腕の付け根・股・尻尾の付け根を自然につなぐために、
最初から SDF のなめらかな合成に切り替えた。接合部がきれいにつながる代わりに、細部（指、顔）の彫り込みが苦手という弱点がそのまま造形の評価に出ている。

## 未検証のまま残した点

- スマホ実機での動作と負荷。
- デスクトップGPUや Safari など、ヘッドレスChromium（ソフトウェア描画）以外での表示。
- .blend を Blender の GUI で開いての確認（bpy からの保存・再読込のみ確認）。Blender 5.3 より古い版で開けるかも未確認。
- 垂れ布と体の貫通の全フレーム確認。
- ゲーム本体（`src/`）への組み込み。当たり判定とフレームデータの整合。`startup` / `active` / `recovery` は動きに合わせた目安で、ゲームバランスの検討はしていない。
- 身長比（moguzo 0.60 / pisuke 0.63 / godan 0.66）は仮の値。
- トゥーン表示は静止画とプレビューで見ただけで、絵作りとしての調整はしていない。
