# マモ拳3D：キャラクリエイト＋自作キャラ探索ストーリー 実現性・基本設計 v0.1

> **ステータス：設計のみ／ユーザー未承認／実装禁止**  
> 2026-11-23。設計の参照元はThree.js 3D v15.1 統合 [PR #199](https://github.com/nagi300222/mamo-ken/pull/199)（HEAD `78dd0c685d78af617896c01bd95a277928e01368`）。  
> **別件の製作指示**：[KO・VS・9勝利映画 #201](https://github.com/nagi300222/mamo-ken/issues/201) と [ARCADE・SURVIVAL #202](https://github.com/nagi300222/mamo-ken/issues/202) は実装依頼として進めてよい。**この企画 #203 は本人が設計を確認して明示的にGOを出すまで、デモ・GLB・ゲームUI・フィールドを一切実装しない。**

## 1. 結論

**実現可能。** 現在の3Dモデルはゼロからスカルプトしただけではなく、Blender/Pythonでパラメータ生成された9つのスキンメッシュと骨格・GLBアニメーションを持つ。既存の対戦エンジンも独立したBattle/CPU/技データを持つ。これらを土台にすれば、自作アバター／模様／戦闘スタイル／技混成／ランダム敵／3Dマップから対戦へ遷移できる。

ただし現状のGLBはすでに「着替えられる完成パーツ」に分解されているわけではなく、**体＋アクセサリーはほぼ一体のメッシュ／UVアトラスへ焼き込み**。尻尾の長さによりボーン数も異なる。別の体型へそのまま別キャラの手・足・尻尾や攻撃モーションを入れると関節と打点が破綻する。**キャラクリ機能の中心は新しい「アバターファクトリー＋スキル互換変換」層**であって、既存選択UIに色ボタンを足すだけではない。

## 2. 現行資産に関する確認事実

**モデル生成**：[characters.py](https://github.com/nagi300222/mamo-ken/blob/78dd0c685d78af617896c01bd95a277928e01368/exp/fable-3d/tools/mamo3d/characters.py) に9体の頭・耳・胸・拳・足・尻尾・色・アクセサリー選択パラメータ。`body.py`が毛並みのSDF/メッシュを生成、[model.py](https://github.com/nagi300222/mamo-ken/blob/78dd0c685d78af617896c01bd95a277928e01368/exp/fable-3d/tools/mamo3d/model.py)がbody/extrasを一つのSkinnedMesh用Meshに結合して一つのUVに展開し、`texture.bake`で色を画像に焼き込む。**現在のGLBは独立した「耳メッシュをワンタップで交換」する形式ではない**。

**骨格**：[rig.py](https://github.com/nagi300222/mamo-ken/blob/78dd0c685d78af617896c01bd95a277928e01368/exp/fable-3d/tools/mamo3d/rig.py) に共通 `root_ground/pelvis/spine/chest/neck/head/jaw/shoulder/upper_arm/forearm/wrist/paw/thigh/shin/foot`等。手足は各L/R、尻尾は通常3本程度、バレットは6本という差がある。レスト姿勢と腕脚比率は9体で違うので、同じ名前の骨であっても**動作の直接コピーは保証しない**。

**色と模様**：[texture.py](https://github.com/nagi300222/mamo-ken/blob/78dd0c685d78af617896c01bd95a277928e01368/exp/fable-3d/tools/mamo3d/texture.py) に毛色、マスク、額筋、毛並みのベイク処理。単純な`material.color`乗算では鼻・腹・毛並み陰影まで巻き込むので、**部位IDマスクを別テクスチャ/Shaderで指定する**方式が適している（素材の作り直しは必要）。

**モーションと対戦**：9体のGLBと独自通常6×9、必殺3×9、奥義9。通常技はスキン後の実測攻撃面と`normal-contacts-v151.js`のreach/heightを合わせている。動作互換/再計測には [Three.js SkeletonUtils.retargetClip](https://threejs.org/docs/pages/module-SkeletonUtils) 等を検討できるが、特に尾/投げ/奥義は新規クリップ補正が必要。

**ロジック結合**：[battle.js](https://github.com/nagi300222/mamo-ken/blob/78dd0c685d78af617896c01bd95a277928e01368/exp/fable-3d/dojo/battle.js) の`fighter.id`が表示・能力・技選択・リーチ計測・専用演出のキーとしても使われている。カスタムアバターでは外見・スタイル・技のそれぞれのIDを**独立させる拡張**が必要。

**現在のマップ**：[dojo/main.js](https://github.com/nagi300222/mamo-ken/blob/78dd0c685d78af617896c01bd95a277928e01368/exp/fable-3d/dojo/main.js) は左右に歩く格闘専用1軸アリーナ。自由移動の3Dフィールドは今は存在しない。対戦エンジンまで3D自由移動に作り直す必要はなく、フィールドは別シーンにできる。

## 3. アバター設計（本人の希望を実現するためのAI初期案）

### 3-1. 外見は9骨格ベース＋自由カスタム

ユーザーは9体のいずれかの体格/骨格を基準に選ぶ。ゲームの移動/当たり判定は一律のスケーリングではなく、選んだ骨格とスタイルに合わせて元の自然な見た目を保つ。

アバタービルダーの画面順（提案）：

1. 名前（ローカル保存）→**ベース体格9種**（初期開放）
2. 頭・耳の形、尻尾の形/長さ、前脚/手、後脚/足、アクセサリーを選択
3. 毛色（主色・腹・耳内・口元・拳/足）、差し色・アクセサリー色はカラーパレットで自由に変更
4. 模様（「なし」「額の筋」「背中の縞」「斑点」「左右非対称」等の複数プリセット）と模様の色・大きさを変更
5. 対戦スタイル（9体から1つ）→技編成→実際の見た目と打点をプレビュー→名前付き保存

**部品ソケットの設計**：`head/ear.L/ear.R/tail.root/tail.segments/paw.L/R/foot.L/R/neck/waist`を定義し、装着パーツには元骨格基準スケール・回転/スキンボーン名・揺れ/干渉/パフォーマンス情報を付ける。体型が違っても装着可能なものと、特定ベース用のものを区別。最初から9×9×全組合せの大規模生成をせず、同じ種類の骨格から3〜4種の最小スキン付き部品を抽出して品質を証明する。

**素材の作り方**：既存のPython/Blender作成フローを拡張し、出力段階で`body parts`を結合しない（または元パーツの頂点/材質グループを保持して分離）方式と、色を変えられるregion maskを持つ出力を追加。実装までの移行は元9体GLBを書き換えず、`custom/parts/`等の別アセットに限定。

- パーツの切り替え：専用の`SkinnedMesh`/骨ソケットの差し替え
- 色：腹・毛・口元等の領域マスクとパレット色パラメータ
- 模様：独立UVパターンマスク＋色/拡大/位置パラメータ
- 毛質感：現行の毛束/陰影を保持し、ベタ塗りにならないよう元の輝度情報を活かす
- 保存：設定JSONを保存（全組合せをGLBファイルとして保存する必要はない）
- パフォーマンス：必要な装飾だけ読み込み、同じ見た目のモブはSkinnedMeshの骨と素材を必要に応じて共有/複製。複製時は正しい骨結合が必要（Three.js `SkeletonUtils.clone` 等）。

### 3-2. 9戦闘スタイルと他スタイルの技

本人の希望：**9キャラから戦闘スタイルを選ぶ**。そのうえで**別スタイルの技も選べる**。全キャラの専用技・奥義アニメ/能力を無制限にコピーできるわけではないため、段階的に動作契約を用意する。

**AI初期ルール案（本人未確定）**：

- スタイル = `styleId`。移動速度/ジャンプ/HP/ガード/Drive/通常6技/固有能力1つの基本セット。ユーザーの見た目（`appearance`）とは別。
- 装備技 = `loadout`。初期案は**必殺1〜3を9体の27必殺から自由選択**。ボタン位置と入力（方向＋必殺）は維持。技はそれぞれ個別の`MoveRef`で登録し、元スタイル由来のデータ/モーション/FXを紐付ける。
- **通常技6種の個別入替や奥義の他スタイル混成も最終的には対応可能**だが、最初の試運転では基本スタイル由来を維持して確認する。奥義9本の既存映画は特定の攻撃者/被弾者造形を想定しているため、カスタムアバター用の汎用カット/代替モーションが必要。
- 1人のカスタムアバターが持つ固有能力は原則選んだスタイルの1つだけ。9種の固有能力を無差別重ねがけしない。
- **技の全スタイル混成のユーザー体験は維持**しつつ、尾薙ぎには長尾パーツ、掴みには手/体型の演技互換、飛び道具には発射点、当て身には専用反応などの必須条件がある。条件を満たさない場合は「必要パーツを装着する」または「安全な代替モーションへ変換する」の2方式を設計する。選択技が黙って消えたり、透明リーチだけ伸びたりしてはいけない。

**技互換変換パイプライン（設計）**

`sourceMove → MoveRef＋必要パーツ/骨/アクション条件 → source AnimationClip → avatar rigへリターゲット → 本人アバターのスキン後の打撃部位表面を再計測 → 必要ならモーション側を直す → 成功した当たり判定/FX/音をロードアウトとして保存`

**固有キャラ名にベタ書きの特例**：現Battleには`if (p.id==='...')`等で能力・技派生・CPU行動・演出が結び付く部分がある。このため`p.id='custom'`にするだけでは既存の9体の技を自由に組み合わせられない。作業を始めるなら、戦闘の核を`styleId/abilityId/moveId/visualRigId`の参照へ分離し、既存9体の動作テストを完全維持する。

## 4. 3Dフィールドで自作キャラを動かすストーリーモード

ゲームをオープンワールド格闘へ作り変える必要はない。**探索中は3D自由移動、対戦開始時だけ既存の左右格闘画面へシーン遷移**するのが安全で早い。現ゲームのスマホ横持ち固定・6ボタン・必殺入力・奥義ムービーを引き継ぐ。

### 最小の試運転案（本人の実装GO後に限る）

- 場所：狭い**集落の広場**など小型フィールド1つ。床・数個の障害物・建物の簡易形状。広大なマップ/シナリオ/装備/レベル上げ/オンライン要素は入れない。
- 操作：スマホ左スティックで360度移動、必要なら右側の「調べる/話す」ボタン、カメラは後方やや上から追従（PCではキーボードも）。
- NPC：**既存9体のうち少数を登場**させ、顔が見える近さで「話す」→一往復の短い会話→「勝負する／戻る」→格闘場面へ。ユーザーが選んだ自キャラがそのまま自機として戦う。
- 敵：既存9体のほか、**seedを保存した自動生成モブ**を少数配置。外見・戦闘スタイル・技は互換性制約/戦闘予算に従い生成（例：体格/模様/色/アクセサリー/レベル、技ランダム）。同じseedで同じ敵を再現可能。
- 復帰：勝敗後は3D広場の元の座標・カメラへ戻す。NPCのセリフと勝敗フラグを更新。途中でブラウザを閉じても保存/再開できる。プラクティス/VS CPUのBattleの既存ロジックを維持。
- コンテンツ：ストーリーの本筋（なぜ旅をするのか、全9体が何を教えるのか、成長/エンディング）は**本実装前に別途企画**。試運転は「会話→戦闘→帰還」の1ループが目的。
- 仮の実装境界：`AvatarEditor`、`AvatarFactory`、`MoveCatalog`、`CombatStyleAdapter`、`OverworldScene`、`DialogueTrigger`、`EncounterController`、`StorySave`。現行`Battle`と`Practice`の直接上書きを避ける。

## 5. ランダムモブの設計

単純に全27必殺・9体能力を無制限ランダム装備すると、不可視技や極端な永久連係が生まれ得る。**外見と強さは独立してランダム化**する。

- `seed`から体格ベース1つ、互換パーツ/色/模様、スタイル1つ、適用可能な技3つを選ぶ。高火力・無敵・長射程・装甲が一個体に重ならないように重み/予算を設ける。
- 尻尾技等に必要なパーツがなければ最初から別技/代替アニメを選ぶ。二重能力や存在しないモーションは不可。
- 名前は小さな固定語彙＋色などで構築し、他キャラと区別して表示。個人情報は不要。
- 戦闘時はスタイル対応のHP/技表と実アバターの技の到達距離を使用。透明射程・背面ヒットが復活しないよう現v15.1の表面計測と攻撃高さ判定を継承。
- 同じseedを入力すれば同じ敵が出る。ランダム対戦結果を同一条件で再試験できる。
- 生成された自キャラとモブ双方で勝敗/KO/勝利ムービーを壊さない。既存9体だけの専用奥義は汎用/互換カメラで扱いを決める。

| 段階 | 目的 | 合格ライン |
|---|---|---|

複数シーン/SkinnedMeshやマテリアルを一度に読み込むとスマホで負荷が増える。既存v15.1の60Hz入力、FPS/熱/メモリ、グラフィック負荷・9奥義/Practiceをベースラインとして、**機種・実測前にFPSを保証しない**。不要なGLB/Texture/アニメをアンロードし、敵表示数を制限。色の変更は毎フレーム大規模なテクスチャ再ベイクをしない。iOSの真の横画面アプリ化は別課題であり、探索画面を作っただけでSafari/OSの縦向きUI問題が直るわけではない。

## 7. この設計で先に本人が選ぶとよい3点

1. **「技の自由さ」優先？** 尾技を尾なしキャラにも使いたいか。案A＝必要な身体パーツ装備を要求／案B＝使えるように技の見た目を別モーションへ置き換える。最終的な技混成にはどちらかの基準が必要。
2. **外見の自由さ**：最初は9骨格ベース＋部品/色/模様で始めるか、さらに体格スライダー（頭/腕/身長）まで初期に必要か。無制限スライダーは技のリーチ・クリップ変換検証が急増する。
3. **試運転の3Dカメラ**：後方追従で広場を歩く案を初期候補とする。俯瞰見下ろしなどへの変更も可能（実機操作/負荷の確認が必要）。

**この文書は技術的に可能な方針を説明する設計提案。本人が「この案で試作してOK」と明示するまではStory/Creatorのコード・GLB/フィールド・ルート/モブを作らない。**
