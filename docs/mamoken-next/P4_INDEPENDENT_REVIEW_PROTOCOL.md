## 1. 何を評価するか／してはいけないか

- 対象：P0/P1 #215、P3素材 #216＋戦闘 #219、P4アート #218＋UI #217、およびP1本人確認後にのみ実装されるP2 #211 を、**1つの固定コミットSHA**で統合した `マモ拳` の本物の画面・操作・音・導線。
- #209はv16機能基準、#214と [P4_VISUAL_DIRECTION.md](P4_VISUAL_DIRECTION.md) は意図を読む資料。#218の合成画像やFigmaのデザイン稿は**評価補助**であり、実装・実機証拠ではない。
- 本人のP1承認がなければP2のコード／GLBの制作に進まない。P4レビュー体制の設置は、この着手ゲートを解除しない。
- **作品のどこを参考にしたかより、使う人の判断や行動をどう助けたか**を評価。桜井政博氏本人の監修・認証と呼ばない。SF6やスマブラの素材/配色/固有の形を複製しない。
- ブラウザテスト、Simulator、物理iPhone、Figma稿、本人試遊は**別々に記録**。一方のPASSを他方へ流用しない。

## 2. 公式動画から翻訳した検査原則

| 桜井UI編の主題（公式動画の項目） | マモ拳で観察する行動・証拠 |
|---|---|
| J-01 わかりやすさとスタイル性 | 山の大会・旅札・マーモットの個性がわかり、初見の選択や文字の読みにくさを増やしていない |
| J-02 文字の大きさ、J-05 文字の強調、J-08 大事なものを大きく | HP、時間、選択/戻る、エラー、次の行動が迷わず読める。装飾や見出しの重複より主目的が大きい |
| J-03 現代の親切設計、J-04 ロード画面 | 初回/再訪の説明差、戻す/取り消す、保存や通信/GLB読込状態の説明、スピナーが固まったままにならない |
| J-06 メニューで世界観を表す、J-07 色分け | 全5モードの共通言語があり、色に加え形・ラベル・位置でも区別できる |
| J-09 すばやく選ぶ、J-10 スキップ/ポーズ | 決定と戻るが素早く、VS/勝利/奥義を必要時スキップ可能。再戦/試合進行は誤って始まらない |
| J-11 ボタン設定、J-12 テキスト送り、J-13 メニューヘルプ | 操作方法や代替手段の表示・変更可否を確認、台詞を進められる。ヘルプはボタン名の言い換えに終わらず結果を説明 |
| J-14 言葉がなくても伝わる、J-15 HUD | アイコン・強弱/危険状態が初見でも読み取れ、相手と自キャラの動きをHUD/指/演出が隠さない |

一次資料：[公式 UI1 J01〜08](https://www.youtube.com/watch?v=9LKqeXQl31U) ／ [公式 UI2 J09〜15](https://www.youtube.com/watch?v=O8b0I6r8p5I) ／ [公式 HUDs](https://www.youtube.com/watch?v=a_HB81ujHHE)。

追加の比較観点：
- **Street Fighter 6**：勝負中のHP・資源・タイマーが対戦の読みを邪魔せず、入力簡略化と熟練操作を両立する考え方。[Capcom公式 操作タイプ](https://www.capcom-support.com/hc/en-us/articles/7122030981660-What-are-the-control-types-in-Street-Fighter-6)。
- **スマブラ**：多くのキャラの顔/名前をすぐ見つけられ、選択状態・確定・ルールが混線しない。初心者も「選ぶ・戻る・遊ぶ」に早く到達。[キャラ選択の構造資料](https://www.ssbwiki.com/Character_selection_screen)。
- これらは観点であって、画面の模写指示・数値品質の保証ではない。

## 3. 6軸のスコア（0〜4、合計100点）

| ID | 軸 | 重み | よくある失敗例 |
|---|---|---:|---|
| A | 理解・視線誘導 | 25 | 最初の5モードが並列に見える／下に続く項目の存在が伝わらない／キャラの差が分からない |
| B | 操作・反応の納得感 | 25 | 親指で誤押し・二重入力、押したか不明、スキップや戻るが効かない |
| C | 独自性と全モード統一 | 15 | 他ゲームの意匠をなぞる／木札と格闘HUDが別作品／状態別のアイコンが不統一 |
| D | 試合の判読性 | 15 | ゲージの変化・相手の打撃/弾道が見えない／重要な位置をエフェクトが覆う |
| E | アクセシビリティ | 10 | 文字が小さい／色だけで警告／減光・音なし・操作方法の検証不足／safe area不適合 |
| F | 進行の快適さ・復元 | 10 | メニューが深い／進行・保存が不明／ローディング・ポーズ・戦闘後復帰が不安定 |

- 0＝不成立、1＝目的に重大な障害、2＝部分的成立だが改修が必要、3＝想定利用で問題なく理解・使用できる、4＝楽しさや情報の説得力まで高水準で成立。
- `点数 = Σ(重み × 評点 ÷ 4)`。審査員は **各軸に必ず「観察できた事実」「改善すべき点」「証拠へのリンク」**を書く。デザイン担当・実装担当は同じPRの唯一の審査員にはなれない。
- **提案合格**は総合85点以上＋全軸3点以上＋重大ブロッカー0。これは完成品を自動保証する数字ではない。人間/物理実機/G0〜G5が未確認なら `保留`。
- 生の実測（タップミス、選択にかかった時間、FPS、チュートリアル介入数）と主観点数を混ぜない。時刻・端末・対象SHAを付記する。

## 4. G0〜G5 評価ゲート

- **G0 統合実体**：Workが「統合Draft PR URL／HEAD SHA／P1確認記録／P2の状態／5モード構成／採用アセットSHA」を記載。作業レーン別のPR状態と区別。統合PR不在ならG0未確認。
- **G1 再現可能な機能試験**：Codexが同一SHAで Node・build・実WebGL（CPU種類・解像度付き）を実行。9体、54通常、27必殺、9奥義、5モード、保存と帰還、Story/道場のHUD・入力同一性、ポーズ/スキップ/復帰。既存CI履歴の再利用時は `sha` 一致を証明。
- **G2 画面・演出の独立レビュー**：ミオ/独立審査者が構図案・実WebGLキャプチャ・短い操作動画を比較。各6軸を採点し「意図→実画面→利用者行動→不一致」を書く。模倣の有無も確認。
- **G3 人間テスト**：少人数の探索的評価。初見2名・格ゲー経験2名を**推奨**（統計的な一般化はしない）。説明せずタスク提示、初回操作/迷い/誤タップ/戻り/選択時間を観察。ナギ本人のP4一括試遊は別の重要な判断。参加者が揃わなければ人数を明記して未評価項目を残す。
- **G4 物理iPhone**：横向き固定＋回転ロック、ノッチ／safe area、両親指で対戦中の接触点を隠さないか、SE OFF・モーション軽減、背景復帰、10分連続時のFPS/発熱/電池の記録。Simulator/Chromeの合格を転記しない。
- **G5 本人のまとまった試遊と判断**：P4統合まで小刻みな判断を求めない。ナギの試遊で `採用／改善して再評価／差し戻し` を決める。P5の企画・調整へ進むが、mainマージ・本番公開は別判断。

ゲート判定は `PASS | FAIL | UNTESTED`。未試験を「問題なし」に変換しない。P1未承認ならP2は未着手のまま、G0/G5は保留。独立審査結果が良くても統合前のPR単体ではP4総合PASSにしない。

## 5. 使う人のタスクシナリオ（無説明で観察）

| ID | 実行する行動 | 観察・記録すること |
|---|---|---|
| T01 | 5モードを見て「練習」「普通の対戦」「勝ち抜き」「サバイバル」「旅」を探して開始・戻る | 5モードの発見性、スクロールの気づき、説明介入数、選択時間 |
| T02 | キャラ9体から役割が違う2体を比較し、一人を決定 | 画像・名前・得意/苦手・選択状態・戻るが理解できるか |
| T03 | 通常対戦をプレイしHP・Drive・奥義・残り時間を指し示す | 見る場所、対戦の邪魔、方向＋技、Hit/Guard/Whiffの反応 |
| T04 | 両親指を置いて弱/強/掴み/ギュイーン/必殺/奥義、ステップ操作 | タップ漏れ、誤押し、指による被り、安全領域、個人差 |
| T05 | Practiceで技を試し、キャラ選択へ戻る | 入力補助・ヘルプ発見、パラメータ表示の邪魔、戻りの確実性 |
| T06 | Arcadeで1戦進行、SurvivalでHP持ち越しの結果を見る | 継続状況/HP/次の操作の理解、VS/勝利動画のスキップ |
| T07 | キャラを作る→色/技変更→名前と保存→集落で会話→Battle→元の場所へ戻る→再読込 | プレビュー主役、データ保全、異なる場面の操作UI一貫性 |
| T08 | 演出再生中にスキップ/ポーズ→音OFF→背景復帰→再戦 | 二重KO/入力状態/音漏れ/復帰、未サポート項目は明記 |

- 計測例：各タスクの達成(はい/いいえ)、所要秒数、戻り操作回数、誤タップ、困った箇所、本人の言葉（短い要約と観察事実を区別）。「ユーザーが悪い」と解釈しない。
- 実用の観察対象：`720×320`／`852×393`／実iPhone横向き／物理ノッチ左右／Chrome上の縦向き強制回転。解像度は必要な画面の最低例であり、すべての機種代表ではない。
- 特に #217 の「モード入口の下のカードにはスクロールが必要」という設計は、**残りのモードの存在に初見で気付けるか**を優先的に観察。見逃しがあれば、見た目が綺麗でもA軸減点する。

## 6. 証拠と差分レビュー

レビュー対象ごとに `docs/mamoken-next/P4_REVIEW_SCORECARD_TEMPLATE.md` を複製して記入する。必須項目：
1. 統合PR URL、動くプレビューURL、**SHA**、観察日時、ブラウザ/レンダラ/デバイス
2. 参照デザイン稿の固定版・元素材と実装キャプチャ（同じ状態／スクロール位置／幅）
3. 5モード入口／キャラ選択／対戦HUD／Practice／Editor／Story／VS・KO・勝利／設定のPNGと導線動画
4. G0〜G5状態＋根拠、6軸の点数と理由、T01〜T08の結果、重大問題／再現手順
5. 改善Issueへのリンク、修正PR SHA、再検証。**基準画像の無断上書きは禁止**。変更案と旧画像の両方を保持

スクリーンショットは見た目しか証明しない。入力、効果音、誤タップ、FPS、状態遷移を静止画だけでPASSにしない。キャプチャの収録条件・レンダラーも併記する。

## 7. 不具合の戻し方・責任

- **BLOCKER**：保存破損／主要操作不能／勝敗・入力不整合／物理ノッチと指で主役を常時覆う → 総合FAIL、担当PRへ即差し戻し。
- **HIGH**：迷いやすいモード導線、重要情報が読めない、Storyと通常戦闘HUDのずれ、誤タップ頻発 → 合否保留で改善Issue、修正後にシナリオ再検査。
- **MEDIUM**：文字の大小、間隔、遷移演出の間、個性が弱い箇所 → P4中に優先度判断し修正。見た目だけの不満でも根拠と影響を記す。
- **LOW**：小さな装飾・軽微な演出揺れ → 記録しP5調整候補。

Work＝HEAD/証拠/Issue管理、Codex＝動作修正・再テスト、Claude＝素材/アニメの意図検証と再制作、ミオ＝独立審査・優先順位、ナギ＝P1確認とP4一括試遊・採否。**誰も自分のPRだけを自己採点して完了宣言しない。** 人間テストの参加者は実在の協力者のみ。AIの擬似ペルソナは実ユーザーテストではない。

## 8. マシン可読な報告／再判定

`docs/mamoken-next/p4-review.example.json` を複製して未実施を埋める。レビュー完成時に `node tools/qa/validate-p4-review.mjs <レビューJSON>` を実行。これは**記載漏れと合格条件の論理チェック**だけを行うもので、見やすさ・タップ感・見栄えを自動採点しない。人間のレビューがない限り、真の完成を主張しない。

結果は `#220` に固定SHAとともに添付。差し戻し後は該当シナリオ＋最低限の全モード回帰を取り直して同じフォームで比較する。
