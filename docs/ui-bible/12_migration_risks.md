# 12｜現行UIから移行する際の安全設計と品質負債

## 12-1 なぜ既存CSSの上から直してはいけないか
P4改良版では多数のモード・安全領域・操作ラベルの修正に成功したが、既存の共通ヘッダー、3×3カード、説明文、DOMラベルの構成を土台にしたまま進めた。結果として「どの画面もWebアプリっぽい」「文字を減らしただけでは満足できない」という問題が残った。

新たなデザインの実装は、CSSの後付けで無理に再現しない。新画面の**状態と画面階層を先に定義**し、既存ロジックはAPIとして継承する。

## 12-2 既存の重要資産
| 既存の仕組み | 守る理由 | 移行時の試験 |
|---|---|---|
| 9体GLBと技54/27/9 | 対戦とキャラの同一性 | 元hash、当たり判定、再生タイミング |
| P2パーツ交換26 | 保存・表示互換 | メッシュ接合・未対応の拒否理由 |
| 6攻撃と移動/ステップ | 操作の記憶 | Story/道場同一レイアウト・pointercancel |
| CPUと格闘ルール | ゲーム性の正本 | 勝敗、スタン、フレーム/入力 |
| Arcade/Survival | 連戦の契約 | 2先・HP持越し・CONTINUE/終了 |
| Creator保存 | 信頼性 | 旧データ/新データ再読込、未保存/成功 |
| Story探索/対話/帰還 | 物語の連続 | 視点/座標/会話・Battle復帰 |
| 約10秒奥義／9勝利 | キャラの見せ場 | スキップ・一回だけKO・CPU/時計停止 |
| Capacitor/Cloudflare | iOS/Web併存 | ビルド、safe area、端末回転 |

## 12-3 段階移行モデル
- MIG-0：新デザイン候補選択。実ゲーム未変更。
- MIG-1：別のUIルート/フラグで全体の画面骨組みを構築。旧UIへ安全に戻せる。
- MIG-2：共通HUD/操作、導線、対戦と連戦へ接続。旧ゲームロジックはそのまま使う。
- MIG-3：Creator/Story/結果/設定/ヘルプへ一貫した意匠と入力状態を適用。
- MIG-4：Claudeの正式キャラ素材・音・動的演出を反映、Figmaと実画面の差分を解消。
- MIG-5：自動＋人間＋物理端末で検証。合格後に旧UIの不要コード/重複CSSを根拠付きで削除。
一枚ずつ旧UIと新UIが混在する状態のまま「一貫性完成」としない。ただし実装は独立ルートで段階検証可能。

## 12-4 運用ルール
- Design tokensはFigmaとCSSで出自/バージョン/用途を持つ。
- 表示されない重要情報は永久に削除しない。移動/段階開示を追跡し、ヘルプの到達性と読みやすさを検証。
- UIとデバッグは別の表示レイヤー。FPS/CI/内部契約を一般の人が見る画面に常駐させない。
- 何かを隠す時に障がい・初心者・色覚・音OFFへの影響を考える。
- デザインを3案作っても、選択なしに自動で混ぜてはいけない。
- 文字を半分に減らしただけでデザイン改善成功と呼ばない。元よりゲームの魅力と操作が増したか人間の行動で確認する。
