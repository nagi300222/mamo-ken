これは文字ラフ。実描画は上記HTMLにある。画面領域はゲームエンジン用の区画とタッチ領域で切り分けるが、**舞台の画素を左右で切り落とさない**。仮の推奨位置：
- **WorldLayer**： x0〜852 / y0〜393。Three.js canvasの全画面。
- **HUDLayer**：上部0〜75付近。左右のHP/Ult/Driveと中央時間だけ。補助説明の巨大な背景は持たない。
- **FightFocus**：x230〜610付近（中心座標は目安）をキャラと拳・弾の中心に優先する。ただし全ゲーム空間は可視。
- **LeftControl**：x35〜225 / y255〜387あたり、ジョイスティックと前後ステップ。
- **RightControl**：x610〜834 / y218〜387あたり、ACT-Dが重ならず操作できる形を検討。
- **OverlayEvents**：VS/KO/Resultの時は非活動の攻撃UIを隠す。入力とステージが同時に動くときはタップターゲット以外へのポインターをゲームが受け取れる。
- **Safe area**：ノッチ左右・角丸・下辺の実端末値は動的に取る。上の位置は固定の製品規格値ではない。

## 2. ACT-D：6つの入力の位置を数値化

座標は **852×393** における仮の可視中心(x,y)／半径r（px）、左上原点。実タップ領域は可視形状より広くしてよいが、隣接ターゲットと競合させない。弱は小さく見せても、44px相当の押せる領域を維持する。

| 操作 | D1：安定 | D2：弧強調 | D3：必殺主役 |
|---|---|---|---|
| **必殺** | (778,312), r40 → 直径80 | (778,310), r45 → 直径90 | (779,304), r49 → 直径98 |
| **弱** | (635,329), r17 → 直径34 | (635,337), r16 → 直径32 | (625,337), r16 → 直径32 |
| **強** | (644,282), r22 → 44 | (640,284), r24 → 48 | (634,283), r23 → 46 |
| **掴み** | (689,251), r21（楕円） | (692,252), r20（楕円） | (683,249), r21（楕円） |
| **奥義** | (739,239), r21（楕円） | (737,234), r22（楕円） | (735,226), r23（楕円） |
| **ギュイーン** | 必殺中心から半径54〜76の弧、112〜157度 | 半径57〜81の弧、110〜161度 | 半径61〜83の弧、112〜165度 |

ギュイーンの弧の角度は**現在の操作スペースを検査するために約45〜53度に短縮した試作**。本人の指定は「1/4円のような弧型」なので、厳密に1/4周へ近づけた形・ポイフルのような丸端の造形は**次のグラフィック工程でも比較を残す**。意図を実現した完成図と呼ばない。

### 2-1. 3案の違い
- **D1**：同じ芯の右寄せでもやや平易。初見での押し間違いと指の移動距離を比較する基準。
- **D2**：必殺を大きく、周りの操作を弧に沿わせて親指の軌跡に近づける。マモ拳らしい独自操作の本命候補。
- **D3**：必殺をほぼスライドパッド級まで拡大。方向＋必殺の気持ちよさ優先。ただし弱や奥義への親指移動が遠くなる可能性。

### 2-2. 表示と入力判定を分ける
- 弱の可視直径32pxは特殊な「小さい印」に見せるためで、押せる面を32pxへ縮める指示ではない。
- 目標タップ面は弱・強・掴み・奥義の最低44px相当、必殺は可視円近く、ギュイーンは弧沿いに広い独立Hit target。隣接ボタンの反応領域と重なる場合は、直近操作IDへの安全な判定、もしくは距離を広げる。
- 操作面の表示形状（SVG/CSS）と `data-control` が解決する入力（現行 `battle-ui.js`）を分離。キー Z/X/V/N/B/M と前後ステップF/Rの既定操作は変更しない。
- ギュイーンは文字を「ギュイ／ーン」と不自然に分割しない。弧に沿う本文字と、操作ヘルプでの正式名称を比較。
- 必殺＋方向入力は左スティックの同時保持ができること。奥義は実ゲームの `ready` を信用して判定、見た目だけで入力可否を変えない。

### 2-3. ボタンの7状態（共通設計）
`IDLE`：縁と材質で押せると分かる。\
`FOCUS`：キーボード・パッドの輪郭が消えない。\
`PRESS`：押下瞬間（目標50ms以内）に面/陰影が凹む。\
`BLOCKED`：入力不可理由は状態ガイドで短く。\
`READY`：必殺/奥義の資源と整合。\
`RELEASE/CANCEL`：pointerup/pointercancel/背景復帰時に押しっぱなしが残らない。\
`HIDDEN`：VS・KO・勝利中は非活動の入力を描かない。

この段階のSVG試作が実装済みなのは**見た目の押下反応**だけで、ゲームのコスト、当たり判定、効果音を処理してはいない。

| 1P 奥義 | x70〜312 / y36〜46 | 分割された蓄積・READY | 仮8分割、実単位ではない |
| 1P Drive | x70〜312 / y54〜62 | 分割された残量 | 仮6分割、実単位ではない |

| CPU HP | x518〜793 / y17〜31 | 右から減るHP | ゲージ減少方向の確認 |
| CPU 奥義/Drive | x529〜771 / y36〜62 | 相手の蓄積・使用可否 | 競技上見せてよい状態の確認 |

**目画像は最終的に同じ3Dモデルから切り出し**を推奨。仮HTMLはオリジナルの抽象目イラストであり正式キャラ画像ではない。目アップによるキャラ識別ができないなら、瞬間だけ小さなキャラ名や色を追加して検証する。

### 3-1. 3つのグラフィック案
- **G1 直線競技**：HPは明確な長いバー。奥義/Driveは同じリズムで細く分割。変化は淡々と読みやすく、演出はREADY時だけ。
- **G2 舞台の切れ味**：HPバーの端に短い切り込み、奥義を一段目立たせる。炎の先端だけ色と動きを強める。被弾でHPの読み取りを妨げない。
- **G3 役割分離**：HPは整然と長く、奥義/Driveに太さ・セグメント形・識別の差をつける。視線が下に流れすぎないか確認。
全案でHPは長い競技バー、奥義/Driveは分割、目アップ＋READY火炎＋奥義ボタン変色。分割本数が実資源の整数ストックに相当するかは現行Battleロジックと照合するまでは確定しない。

### 3-2. 奥義が満タンになる瞬間
1. ゲームから奥義READYの状態を受信。残量表示が最後の分割を満たす。
2. **ゲージの先端だけが燃える**。通常時の細い境界が、READY時には暖色の火に変わる。
3. 同フレーム以降、右手の奥義ボタンが未READY色からREADY色へ変化する。ボタンの位置・操作IDは変えない。
4. 低刺激では炎の動きを止めて「光る先端＋明確な輪郭」。音OFFでもREADYが分かる。
5. 奥義が使われた瞬間、発動可否と残量の正しいゲーム状態へ戻す。ムービー発生は**命中時のみ**の既存仕様であり、押下と命中を混同しない。

## 4. LAYOUT-F：全画面ステージ＋少し遅れて追うカメラ

| ID | 優先 | 追従係数の仮候補 | 下部操作の置き方 | 検査したいこと |
|---|---|---|---|---|
| **F1 安定全景** | 操作の安定 | 時定数 `τ=190ms` | スティック少し上、ACT-D少し内側 | 親指とキャラの距離／初見視認 |
| **F2 ステージ重視** | 世界が画面いっぱい | `τ=250ms` | 下部の景色を透かして配置 | 中央の舞台の広がり／スクロール後の見失い |
| **F3 攻防追従** | 速い読み合い | `τ=145ms` | 操作領域をやや上へ | ダッシュ/飛び込みで相手を見失わないか |

**これらは仮の見た目比較用の値で、実対戦カメラの完成パラメータではない。** HTML上の動きは正確なゲーム物理/60Hzではなく、対象を追う印象を見比べるための数理デモ。

### 4-1. Three.jsへ移す場合の追従式（説明用）
```js
const dt = Math.min(clock.getDelta(), 0.05);
const center = player.position.clone().add(enemy.position).multiplyScalar(0.5);
const alpha = 1 - Math.exp(-dt / followTimeConstantSeconds);
cameraTarget.lerp(center, alpha);

// ここからカメラ距離・ズーム・安全なキャラ可視範囲を制約。
// 両キャラ/重要な弾道が右下の操作Hit領域と交差しないよう調整する。
```
- 単に「中点を常に追う」だけだと、互いの間隔が広がったとき片側がボタンに隠れる。**画角/ズームを先に調整し、追従ラグよりも見失わないことを優先**する。
- F2の仮試作は、キャラの表示中心をおおよそx247〜580へ制限し、被りそうなら追従補正を優先。手・尾・弾道が本当に安全かはモデルサイズで検証。
- 左右端に押し込まれたときの画面端・舞台背景の見え方、縦ジャンプ時のカメラY、奥義中の専用カメラから通常カメラへの復帰は新しいテストが必要。
- カメラの追従で遊びのルール（当たり判定・入力方向・ガード）に手を入れない。
- 手前の舞台も背後の舞台も右下UIの下へ描画し、UI以外の意味あるものが見えるようにする。透明度だけ下げてボタン自体が押しにくくなるのは不可。
