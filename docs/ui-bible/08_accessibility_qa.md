# 08｜アクセシビリティ・品質ゲート・人が使った証拠

## 08-1 画面の目的ごとの検査
**分かりやすい**とは、文章が少ないことでも、画面が綺麗なことでもない。*初めて操作する人が、何をしようか迷いすぎずに、期待した結果へ進めること* と定義して観察する。

### 初見の人が行うT01〜T10
| ID | 無説明でお願いする行動 | 記録する具体値 |
|---|---|---|
| T01 | 5モードから練習を見つけて開始 | 発見時間、途中の誤選択、助言数 |
| T02 | 通常対戦で9体から好きなキャラを選ぶ | 迷い、名前/外見の判別、決定 |
| T03 | 対戦前の相手と自分を見分ける | キャラ・色・方向の理解、スキップ |
| T04 | 対戦中にHP・時間・Drive・奥義を指差す | 正答率、視線移動、読めない項目 |
| T05 | 両親指で弱・強・掴み・ギュイーン・必殺・奥義 | タップミス、押下感、誤発火、指の遮蔽 |
| T06 | Practiceで技を試し、練習設定を変えて元へ戻る | 操作数、状態の理解 |
| T07 | アーケードで次の試合へ進む | 進行の見え方、次の操作の発見 |
| T08 | サバイバルで持ち越したHPと戦数を確認 | 表示場所と意味の正答 |
| T09 | キャラクリ→保存→探索→会話→戦闘→帰還→再読込 | 保存の安心感、戻り、データ継続 |
| T10 | 音OFF・演出軽減・Pause/Resume・キャラ選択へ戻る | 設定発見・効果・戻りの不安 |

実際の参加者数と経験は明記し、AIのペルソナや自動テストを人間テストと呼ばない。

## 08-2 検査する端末状態
| 条件 | 何を確認するか |
|---|---|
| 横 720×320（safe area模擬） | 主要CTA・名前・HP・操作の欠け、領域幅 |
| 横 852×393 | 情報の密度と全9キャラの認識 |
| 縦持ちCSS横表示 | 座標系/タップ位置とSafe Area |
| iOS Simulator | ビルド/起動/画面キャプチャ、物理認証とは区別 |
| 物理iPhone | 両親指・ノッチ・実FPS・発熱・SE/遅延、回転・背景復帰 |
| キーボード | TAB/矢印/戻る/決定/ヘルプのフォーカス順 |
| コントローラー | 画面選択・取消・6攻撃・ステップ、入力設定 |
| 音OFF | 音の依存がなく重要状態を理解できる |
| reduced motion | 揺れ/点滅なしでも状態と方向が分かる |
| 長い名前・文字サイズ拡大 | 折返し/切れ/押せないボタンがない |

## 08-3 視認性と触り心地の検査
- 文字の絶対最小値だけでなく、**試合中の視線の移動時間**と**理解に必要な停止時間**を観察。
- 彩度差をなくしても、選択中・失敗・残量不足が分かるか。
- 見た目のボタン領域と実際のタッチ領域が対応しているか。
- 連打で反応音が重なりすぎず、二重開始しないか。
- 新しいUI部品が既存カメラ・3D描画・保存を壊さないか。
- 説明を隠した結果、ヘルプに辿りつけない初見者が増えていないか。
- 「ギュイーン」の文字切れ/折れ、Storyの「後ステ／ップ」「ドライ／ブ」が残っていないか。

## 08-4 デザイン独立審査（新しい品質基準）
従来の6軸100点（#220/#221）は必要だが充分ではない。新しいUIバイブルでは別の「作品としての表現」審査を加える。
| 観点 | 質問 | 合格を裏づける観察 |
|---|---|---|
| 世界観 | 文字を読まなくてもマモ拳でしか見られない場所/キャラが分かるか | メニュー・キャラ選択・村・勝利の関係 |
| 体験の強弱 | どこで静かにし、どこで盛り上げるか | 戦闘中静かなHUD→KOで大きな演出 |
| 意図ある配置 | 形・余白・位置に理由があるか | 何を見て押すか説明できる |
| モードの違い | 5つの遊びの性格が表れているか | Arcade/Suvival/PRACTICE/Storyで別の意味 |
| 操作の共通性 | シーン演出が違っても操作ルールが変わらないか | Battle/Story同じ6ボタン |
| 人への配慮 | 体験の魅力と読みやすさを両立できるか | 親指・視認・音OFF・初見操作 |
| つながり | 1戦をひと続きの作品として感じるか | 音付きの遷移動画と人間の試遊 |

この審査を点数だけに閉じず、「観察」「目的」「代替案」「根拠」「未評価」を必須にする。

## 08-5 差し戻しの優先順位
- BLOCKER：機能不能、データ消失、入力/判定不整合、重要情報の常時不可視、無限ロード。ゲーム完成と宣言しない。
- HIGH：通常戦闘の視認性、全モードへの到達性、保存の可否、戻れない、主操作誤押し頻発。
- MEDIUM：補助文字の読みづらさ、場面に合わない共通ヘッダー、アートの統一不足、音の差。
- LOW：細かな光の強さ、飾り線、アニメの間の微調整。
元の#225でHIGHが消えたことと、新デザインでHIGHを再発させないことは別課題。

## 08-6 静止画→実ゲーム検証
1. Figmaの編集可能レイヤーと選択した状態IDが存在。
2. 同じ機能が実DOM/Three.jsのゲームで動作し、入力/保存/回帰を保全。
3. 同じSHAで720×320、852×393の実WebGL画像・音付き動画と自動検証。
4. モードを跨いだ連続操作の比較動画（Before/After）を保持。
5. 実iPhone・人間による初見操作を行い、未実施なら明確に保留。
6. ナギがまとまった完成版を試し、好みの採否と不満を示す。AIは「ユーザーは気に入ったはず」と補完しない。

## 08-7 UXの過度な自動化を避ける
「AI独立評価」は有効な仮説検査だが、自動AIテストは**本物の好き嫌い・触り心地・音・疲労**を代替できない。既存の81.25点を超えることだけを目標にしない。**画面の存在理由とプレイの楽しさ**を優先する。
