### 0.1 この文書の役割

`docs/03_data_design.md` は、マモ拳の実装へ直接渡す唯一のゲーム仕様正本である。

分割Design Docsは設計理由、検討履歴、詳細説明を保持する。コード、テスト、YAML／CSVは本書の状態ラベルと契約へ従う。

T01では本書だけを置換する。型、挙動、BAL、アセット、`dist` は変更しない。

### 0.2 資料優先順位

矛盾時は次の順で採用する。

1.  ユーザーの最新明示決定
2.  Integrated Designの `01_CURRENT_DECISIONS.md`
3.  本書
4.  Combat Bibleおよび分割Bible
5.  現行コードの監査結果
6.  旧設計書・過去案
7.  一般的な格闘ゲーム知識

コードが本書と異なる場合、コードを無断で正本化しない。`CURRENT_IMPL`として記録し、移行タスクを作る。

### 0.3 状態ラベル

| ラベル           | 意味                                          |
|------------------|-----------------------------------------------|
| `CONFIRMED`      | 設計として確定。変更には明示判断が必要        |
| `CURRENT_IMPL`   | 現行コードまたは既存アセットで確認済み        |
| `PROVISIONAL`    | v0.12系の検証候補。実測前に確定値へ昇格しない |
| `AUDIT_REQUIRED` | コード、実測、サーバ状態の確認が必要          |
| `UNDECIDED`      | ユーザー判断、キャラ設計、素材決定が必要      |
| `LEGACY`         | 履歴保全のみ。新規実装の根拠にしない          |

### 0.4 主要用語

- **スタイル:** そのキャラクターが最も安定して勝率を出せる戦い方。能力名や数値配分の別名ではない。
- **Telegraph:** Startup内で攻撃段・技種を視覚／音で予告する区間。
- **Reach Class:** 自由移動の距離ではなく、通常位置・スウェー・踏み込み状態のどこへ届くか。
- **Knockback Class:** 接触後に密着継続、通常仕切り直し、強制仕切り直しのどれになるか。
- **ギュイーン:** 条件成立時に自動突入する、キャラクター性能非依存の公平な競り合い。
- **BAL:** 戦闘数値の一元管理領域。
- **BossRuleSet:** 対人CharacterDefと分離されたCPUボス専用ルール。

## 1. ゲームルールと変更禁止原則

### 1.1 ゲームの核 — `CONFIRMED`

- マーモット同士の喧嘩を題材にした、スマートフォン縦画面の2D対戦格闘ゲーム。
- 60fps固定ロジック、1ラウンド60秒、2本先取を基準とする。
- 自由移動、ジャンプ、対空、壁・画面端、空中コンボ、通常の起き攻めを採用しない。
- 両者は固定基準間合いで向き合う。
- しゃがみ、スウェー、踏み込みは自由移動ではなく用途の明確な回避行動。
- 攻撃段は上段／中段／下段、崩しとしてつかみを持つ。
- 通常状態の一度の最大コンボだけで試合を決めない。
- 武器は原則禁止。野菜・花・衝撃波などは、マーモットの喧嘩として成立する場合のみ個別採用できる。
- コミカルさを基調とする。ダークモグゾーの極端なダークファンタジー表現は、本人の真剣さと見た目の落差が笑いへつながる場合に採用できる。

### 1.2 読み合い優先 — `CONFIRMED`

新システム、新ゲージ、新ボタン、新状態は、次のいずれかを満たす場合だけ採用する。

- 相手の防御選択を動かす。
- リスクとリターンの異なる判断を作る。
- 既存行動への対策と逆対応を増やす。
- 成功条件と失敗理由が画面上で理解できる。

複雑になるだけの要素は採用しない。

### 1.3 読み負けを消さない — `CONFIRMED`

次を禁止する。

- 全技の空振りを無条件でキャンセル。
- 攻撃後に常時即ガード。
- ヒット／ガード／空振りの全てで安全な高火力技。
- 防御成功なしのカウンター専用追撃。
- 常時スーパーアーマー。
- 同じ通常技だけの永久連携。
- 時間経過だけでCharge最大。
- キャラクター性能によるギュイーン優遇。

### 1.4 ギュイーン完全公平 — `CONFIRMED / 変更禁止`

次へキャラクター、スタイル、難易度、BossRuleSetの差を付けない。

- 発生条件
- ミニゲーム抽選率
- 制限時間
- 入力判定・猶予
- 勝利ダメージ
- 奥義ストック獲得
- その他の報酬

CPUのミニゲーム実行精度は難易度configへ置けるが、`charId`を条件にしない。

### 2.3 BattleFlow — `CONFIRMED CONCEPT / 実コード名AUDIT_REQUIRED`

最低限、次を通常入力と分離する。

``` ts
type BattleFlow =
  | 'intro'
  | 'fight'
  | 'gyuiinIntro'
  | 'gyuiinSelect'
  | 'gyuiinPlay'
  | 'gyuiinResult'
  | 'ultActivation'
  | 'ultCinema'
  | 'koCinema'
  | 'roundResult'
  | 'matchEnd';
```

### 2.4 決定論 — `CONFIRMED`

- core内で`Math.random`を使用しない。
- core PRNGとAI PRNGは別系列にする。
- 同じseed、同じ入力イベント列、同じバージョンで同じ状態hashを生成する。
- 1tick内の処理順を固定する。
- 小数処理、補正、丸め順を固定する。
- 描画、VFX、SE、アニメーションの遅延で勝敗を変えない。
- オフラインとオンラインで戦闘判定を分岐させない。
- T02以降の各機能PRで、2クライアント長時間デシンク検証を必須とする。

### 2.5 1tick処理順 — `CURRENT_IMPLを基礎にT00監査`

``` text
1. raw入力をInputEventへ変換
2. 入力履歴・hold状態・先行入力を更新
3. 行動受付とコマンド解決
4. FighterPhase / BattleFlowを進行
5. 接触候補を収集
6. 同時接触・防御・回避・投げ・アーマーを固定順で解決
7. ダメージ、Guard、Gauge、Combo状態を更新
8. Guard Break、Down、KO、Ult、Gyuiin遷移を解決
9. Hitstopとtimerを更新
10. 描画向けイベントを発行
11. 状態hashを生成
```

同一FでKO、奥義ストック3、ギュイーン条件が重なる場合の優先順位は `AUDIT_REQUIRED`。T00で現行挙動を記録し、意図しない差だけを別タスクで直す。

### 3.3 固有能力契約 — `CONFIRMED CONCEPT`

- **根性:** 異なる技を使用した時だけ次のコマンド補正を小幅緩和。低HP時にごく小さい攻防補正。同技反復とギュイーンへ影響しない。
- **チェイス:** Knockback 0技とヒット時ステップキャンセルを多く持つ。単発火力と始動補正は低い。同じボタンだけでは攻めが切れる。
- **ヘビーアーマー:** 指定された重量技の一部に、Startup途中から1Hitアーマー。常時アーマーは禁止。
- **アイアンウォール:** ガード、正解回避、ジャストステップ成功後、次の一技だけ発生またはGuard Damageを強化。投げには無効。
- **フェイント:** 一部コマンドをTelegraph中にキャンセル／ディレイ。専用硬直を持ち、即確定択にしない。
- **プレッシャー:** 打撃から投げ属性技、一部投げから専用補正コンボ。主入力は攻撃ボタン終端のヒットグラブ。
- **ジャスト:** 正解回避／ジャストステップ成功時だけ専用追撃。通常状態の崩しは低い。
- **オーバーチャージ:** 能動的成功でCharge 0〜3。段階に応じ同じMoveSpecが変化し、MAX技で全消費。

## 4. 入力レイアウトと入力イベント

### 4.1 スマートフォン縦画面契約 — `CONFIRMED`

- **左上:** つかみボタン。
- **左上半分:** ホールドでガード、短いジャストタップで見切り。
- **左下半分:** `← / ↓ / →` の方向ボタン。
- **右側:** タップ高さで上段／中段／下段。
- **右側フリック:** 咆哮操作。現行ジェスチャー境界はコードを正として監査する。
- **奥義ストック3:** 発動画面へ入り、タップで即時発動。
- **ギュイーン中:** 通常入力を停止し、各ミニゲーム専用入力へ切り替える。

方向ボタンは回避入力とコマンド履歴の二重用途を持つ。

### 4.2 InputEvent — `TARGET_v0.12`

``` ts
type InputEvent =
  | { t: 'attack'; level: Level; frame: number }
  | { t: 'grab'; frame: number }
  | { t: 'guard'; held: boolean; frame: number }
  | { t: 'mikiriTap'; downFrame: number; upFrame: number }
  | { t: 'direction'; dir: Direction; frame: number }
  | { t: 'roar'; frame: number }
  | { t: 'ultTap'; frame: number }
  | { t: 'gyuiinPick'; value: string; frame: number }
  | { t: 'gyuiinTap'; frame: number }
  | { t: 'pause'; frame: number };
```

raw pointer座標、gesture判定、InputEvent、コマンド認識、行動受付を分離する。UIはcoreへ直接行動を確定させない。

### 4.3 同時入力の原則 — `CONFIRMED`

- つかみ領域は攻撃高さより優先する。
- ギュイーン、奥義発動、Pauseなど専用flowでは通常戦入力を無効にする。
- 複数指入力の受付順はInputEvent列へ固定し、P1／P2と端末差で変えない。
- 2P視点では見た目の左右を反転しても、論理方向を統一して記録する。
- Pause解除時に押下状態を持ち越さない。

## 5. コマンド認識と受付窓

### 5.1 用途別受付 — `CONFIRMED / PROVISIONALを分離`

``` ts
interface CommandTiming {
  commandPrebufferF: number;
  tapFlickLeniencyF: number;
  directionHistoryF: number;
  directionGapMaxF: number;
  commandTotal3F: number;
  commandTotal4F: number;
  finalButtonGraceF: number;
  sameDirectionMinGapF: number;
  holdDetectF: number;
  chargeCompleteF: number;

```

| 値                     | 数値 | 状態           | 用途                                                 |
|------------------------|-----:|----------------|------------------------------------------------------|
| `commandPrebufferF`    |   12 | `CONFIRMED`    | 硬直終了前に完成したコマンドを行動可能Fで発動        |
| `tapFlickLeniencyF`    |   10 | `CURRENT_IMPL` | 旧`INPUT_BUFFER`の実用途。タップ／フリック判定の遊び |
| `directionHistoryF`    |   24 | `CURRENT_IMPL` | 方向入力履歴                                         |
| `directionGapMaxF`     |   18 | `PROVISIONAL`  | 隣接方向間の最大受付                                 |
| `commandTotal3F`       |   28 | `PROVISIONAL`  | 3方向列全体                                          |
| `commandTotal4F`       |   38 | `PROVISIONAL`  | 4方向列全体                                          |
| `finalButtonGraceF`    |   10 | `PROVISIONAL`  | 最終方向から攻撃まで                                 |
| `sameDirectionMinGapF` |    2 | `PROVISIONAL`  | 同方向連打のチャタリング除外                         |
| `holdDetectF`          |   30 | `PROVISIONAL`  | 長押し認識                                           |
| `chargeCompleteF`      |   45 | `PROVISIONAL`  | タメ成立基準                                         |

一つの`INPUT_BUFFER`へ再統合しない。

### 5.2 コマンド優先順位 — `CONFIRMED`

1.  条件付き派生が成立している完全一致
2.  より長い方向列
3.  より具体的な完全一致
4.  通常のコマンド技
5.  単方向回避
6.  通常攻撃

最長一致を待ちすぎて入力遅延を作らないよう、成立時点と保留条件をテストで固定する。

### 5.3 コマンド体系 — `CONFIRMED`

- 全キャラクター共通の3技上限は廃止。
- 完成体系は基本コマンド技7個＋特殊技1〜2個。
- 既存3キャラクターの既存3技は、技枠1〜3として継続採用する。
- 既存3技の数値、役割、入力、派生は再検証し、問題のある技だけ個別改修する。
- 難易度は入力窓の狭さではなく、方向列の長さ、派生判断、条件管理、ルート選択で作る。
- 方向＋つかみ終端は少数に限定する。
- グラップラーの主な投げは、攻撃ボタン終端の投げ属性技を中心にする。

### 5.4 入力難易度配分 — `PROVISIONAL`

| 難易度 | 初級 | 中級 | 上級 | 特殊 |
|-------:|-----:|-----:|-----:|-----:|
|      1 |    4 |    2 |    1 |    1 |
|      2 |    3 |    2 |    2 |    1 |
|      3 |    3 |    2 |    2 | 1〜2 |
|      4 |    2 |    3 |    2 |    2 |
|      5 |    2 |    2 |    3 |    2 |

例：

- 初級: `↓→ / ↓← / ←→ / →← / ↓↓`
- 中級: `→↓→ / ←↓← / ←↓→ / →↓←`
- 上級: `↓→↓→ / ↓←↓← / ←→←→ / タメ / 条件派生`

## 7. 打撃・投げ・ガード・見切り・回避

禁止：

- 時間経過だけの自動増加

- 同一行動反復で効率よく最大化

段階に応じ同じコマンド技の性能、派生、コンボルートを変える。MAX技は全消費し、一時的にパワー型を超える瞬間火力を許可するが、通常時平均はパワー型未満にする。

## 12. CPU・難易度・Persona・ボス

### 12.1 公平性 — `CONFIRMED`

CPUへ次を渡さない。

- プレイヤーの未公開入力
- 入力buffer
- コマンド候補
- 将来乱数
- 未表示Move分岐
- core内部の秘密状態

CPUは公開Telegraph、現在phase、HP、Guard、Gauge、過去行動などallowlistだけを観測する。

### 12.2 難易度 — `CURRENT_IMPLを基礎`

- EASY
- NORMAL
- HARD
- デフォルトNORMAL

難易度は反応遅延、正解率、見切り試行、回避試行、攻撃頻度、コンボ継続判断、ミニゲーム実行精度を変える。

禁止：

- 0F反応
- 確定正解
- 入力読み
- ギュイーン抽選・報酬の変更
- キャラ別の隠し補正

### 12.3 Persona — `TARGET_v0.12`

Personaは難易度と分離する。

例：

``` ts
interface AiPersona {
  reactionRangeF: [number, number];
  aggression: number;
  guardBias: number;
  mikiriBias: number;
  dodgeBias: Record<'crouch' | 'sway' | 'step', number>;
  attackWeights: Record<Level, number>;
  grabBias: number;
  roarBias: number;
  riskTolerance: number;
  repeatTolerance: number;
}
```

同じHARDでもキャラクターの勝ち筋に沿う行動傾向を作る。CPUだけの性能値をCharacterDefへ混ぜない。

### 12.4 ダークモグゾーCPUボス — `CONFIRMED RULE`

対人`CharacterDef`と`BossRuleSet`を完全分離する。

v1の強化手段：

- 既存技の攻略可能な派生
- HP帯・ラウンド等による行動フェーズ
- 行動重み
- 1試合1回限りのBossRuleSet

完全新規の専用技は必須にしない。

禁止：

- ボス補正を対人版へ混入
- 未公開入力読み
- 0F反応
- ギュイーン差
- 常時無敵
- 反撃不能な不可視強化

具体的なHP、Guard、Armor、Damage、1回限りルールの効果、解禁条件は`UNDECIDED / BAL`。

``` ts
  ultMode: 'A' | 'B';
  cpuDifficulty: 'easy' | 'normal' | 'hard';
}
```

localStorage keyとversionは現行コードを監査して記録する。未実装の戦績、解禁、アーケード進行を推測で追加しない。

### 15.2 オンライン — `CONFIRMED PRINCIPLE`

- core決定論を前提に入力交換型で同期。
- 同seed、同入力列、同状態hash。
- 入力受付、コマンド成立、Reach、Charge、Step Cancel、BossRuleSetの処理順を固定。
- BossRuleSetを対人bundleへ送らない。
- P2視点反転で論理入力を変えない。
- ギュイーン、奥義、KOのflowを同期する。
- サーバ変更はローカル確認→発注者deploy→接続確認→マージ。
- T02以降は2クライアント長時間デシンク検証必須。

### 15.3 リプレイ — `TARGET`

seed、バージョン、入力イベント列、必要なルールセットIDを保存し、同じ状態hash列を再生する。

描画イベントは保存せずcoreから再生成する。
